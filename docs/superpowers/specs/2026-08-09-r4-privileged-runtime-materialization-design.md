# R4 Privileged Runtime Materialization Design

**Status:** Approved Option 1 design. This document changes the protected-runtime preparation architecture only. It authorizes neither a privileged invocation nor custody issuance.

## Decision

The unprivileged Python tooling is an input verifier and bundle producer. It must never execute the downloaded CPython interpreter, `pip`, a wheel, `otool`, a compiler, a downloader, or a privileged helper. It validates the exact committed lock and already-downloaded artifacts, creates a user-owned **sealed input bundle**, and emits review evidence. The seal is not authority: a same-UID adversary can replace it.

The installed, root-owned Task 14 Swift helper is the sole runtime materializer. After bootstrap has authenticated its Developer-ID-signed binary and the Task 14 approval, it opens an input bundle read-only, revalidates every expected byte against the approval, copies only accepted regular files into a fresh root-owned private staging directory, and only then extracts the Python archive and installs the pinned wheels through the pinned Seatbelt launcher and final root-owned interpreter. It produces the runtime manifest and receipt from that materialization. It never executes a user-owned interpreter or accepts an output closure made by Python.

This supersedes the old Task 2 assumption that `scripts/prepare_r4_protected_runtime.py` may run the extracted interpreter and `pip`, and the prior V1 provision **prohibition** on `pip install`. The sole replacement is the bounded root-owned offline installation in this document; no other provision-time package operation is authorized. For this fixed authority ID, V1 Task 14 approval parsing, V1 runtime-manifest parsing, V1 receipt parsing, and any mixed V1/V2 evidence graph are retired: they must fail before private staging, admission, extraction, or a child launch. The protected-execution authority's namespace, bootstrap trust anchor, old-custody evidence policy, and separate Task 15 approval otherwise remain as specified in the approved 2026-08-08 designs.

## Explicit V2 authority replacement

The installed helper has exactly one materialization evidence graph for `r4-disjoint-custody-v2-execution-v1`: `R4_TASK14_PRIVILEGED_MATERIALIZATION_APPROVAL_V2` plus V2 input/runtime/authority/receipt schemas. It does not retain a compatibility parser or fallback branch for the V1 forms for this ID. A new authority ID and separately approved design would be required to reintroduce any different graph.

The pre-bootstrap Task 14 approval verification public key (Key A) and the runtime authority/receipt signing key (Key B) are distinct keys with no shared private/public bytes, storage path, signature domain, or rotation path. Key A's SHA-256 is a compile-time constant in the reviewed provisioner Swift source and is therefore covered by the provisioner source and built-binary identities. Its private counterpart remains external to bootstrap and is usable only by the separately authorized approval/authorization ceremony. Key B is a new root-generated generation-1 key created only after Key A has verified the final approval; it signs runtime receipts and has no approval-verification capability.

During `bootstrap-install`, the administrator supplies the final reviewed V2 approval bytes, its detached approval signature, a held absolute Key-A public-key file, and an independently supplied approval digest. The helper accepts exactly the closed `--task14-approval`, `--task14-approval-signature`, `--task14-approval-verification-public-key`, and `--task14-approval-sha256` inputs; there is no caller-supplied expected-key hash. It opens the public-key path descriptor-relatively/no-follow, requires a regular root-owned file of the exact public-key encoding, hashes its held bytes, and compares that hash to the compile-time constant before it verifies the approval signature. It then validates canonical approval bytes and the complete V2 schema, checks the approval's Key-A hash against that same held hash, hashes the **held approval bytes**, validates its own held executable's SHA-256, designated requirement, Developer ID certificate identity, and Team ID against the approval, then atomically stores the byte-identical approval as `bootstrap/task14-approval-v2.json`, its 64-byte detached signature as `bootstrap/task14-approval-v2.ed25519`, the exact Key-A bytes as `bootstrap/task14-approval-verification-public-key`, and its digest as `bootstrap/task14-approval-v2.sha256`. All four are root:wheel, sealed and re-opened by descriptor before bootstrap succeeds. Only after those checks does bootstrap create the distinct root-only Key-B generation-1 receipt key in `control/keyring/`. The installed helper opens only these bootstrap objects; it does not accept a caller approval, signature, verification-key, or expected-key-hash path during materialization.

Key A never self-authenticates: the candidate's Key-A file, its own bytes, a review-package field, an authorization field, an approval field, a signature, or any Key-B keyring record can corroborate only after the compiled constant has accepted the held Key-A bytes. The compiled constant is the sole expected-key value. A mismatch, unparseable key, changed descriptor, or attempt to make the approval select its verifier fails before any signature verification, bootstrap write, Key-B generation, or child launch.

## Evidence and assumptions

### Established Darwin constraints

The design relies on the following observed platform facts, rather than treating a Linux descriptor-execution pattern as available on macOS:

- Darwin provides neither `fexecve` nor `execveat` for this use.
- Executing a regular file through `/dev/fd/<n>` fails with `EACCES`; it is not a safe substitute for descriptor execution.
- Directory descriptors are not executable (`ENOTDIR`).
- `pip` cannot take wheel file descriptors; it needs named wheel paths.
- A `DYLD_*` workaround is invalid: it creates loader authority outside the accepted closure and is rejected.

Therefore execution by an untrusted descriptor is impossible here. A pathname is permissible only after the helper has copied the object into a root-owned `0700` directory, rebound and rehashed it, and prevents every untrusted principal from replacing any ancestor or child. The helper uses a fixed absolute pathname under that private directory, not `/dev/fd`, `PATH`, a relative path, a caller path, or a dynamic-loader override.

Seatbelt activation has one additional non-negotiable Darwin constraint: the helper does not call a private sandbox API, dynamically load a sandbox library, or invoke a generic shell wrapper. Its sole sandbox launcher is the Apple-signed system regular file `/usr/bin/sandbox-exec`; it is invoked by its exact absolute pathname only. The exact profile is therefore a positional `-p` argument, not a temporary profile file, inherited descriptor, environment field, or `sandbox-exec` default. On the inspected target platform its designated requirement is `identifier "com.apple.sandbox-exec" and anchor apple` and Security reports no Team ID; these are schema facts, while the approval pins the current concrete byte and certificate-chain hashes. An OS update that changes any pinned launcher fact is an intentional `SANDBOX_LAUNCHER_MISMATCH`, requiring a newly reviewed policy and approval; it never falls back to a different Apple binary or an unpinned system copy.

### Trust separation

| Evidence or location | Trust meaning | May it execute code? |
| --- | --- | --- |
| Git checkout, downloads, Python bundle, shell environment | Adversarial transport input | No |
| `r4_protected_python311.lock.json` | Committed exact artifact policy | No |
| Input-bundle manifest and user immutable modes | Useful integrity claim, not authority | No |
| Task 14 approval envelope | Reviewed binding of exact input manifest, helper identity, policy, and Git evidence | No |
| Installed Swift helper, bootstrap key, `/Library/...` private staging | Root trust boundary | Yes, only after verification |
| Published protected authority | Sealed execution authority | Yes, after fresh verification |

The bundle is authenticated by the bootstrap-pinned Task 14 approval, not by a user key. A Python-generated detached signature, user immutable flag, or matching filename adds no authority and is not accepted as an alternate proof. The approval carries the expected canonical input-manifest SHA-256 and ordered artifact rows; the helper independently recomputes both from held descriptors before it copies or executes anything.

APFS alone is insufficient.

`materialization-work` is created during bootstrap or by a fixed installed helper only after that preflight and fixed-child validation. Each attempt UUID comes from the helper's cryptographic RNG. Every mutable staging object is `root:wheel 0700` for directories or `0600` for regular files; it is neither exported nor reachable through a user-writable parent. Before publication, final authority directories become `0555`, ordinary files `0444`, private keys `0600`, and every authority object receives and read-backs `SF_IMMUTABLE` as in the protected-execution design. Failure to apply/read back the required ownership, mode, ACL absence, flag, and descriptor/name identity is fatal.

## Closed interfaces and schemas

All JSON is UTF-8 RFC 8785 canonical JSON with no newline, duplicate key, float, unknown key, unordered collection, case-fold collision, or non-ASCII path. `sha256` is the SHA-256 of the exact canonical object with that field omitted. All path rows use normalized POSIX relative paths; regular files have `nlink == 1`; symlinks, devices, sockets, FIFOs, hard links, and unlisted files are invalid.

### Rotation, revocation, and acyclic bindings

Key B alone is subject to the existing root-only keyring/rotation and revocation protocol; materialization has no write path to it. Bootstrap creates Key-B generation 1 after, and only after, Key-A byte/hash/signature verification and bootstrap-object sealing have succeeded. Key B's private key is `control/keyring/generation-1/authority-receipt-ed25519-private-key` (`0600`) and its public key is `control/keyring/generation-1/authority-receipt-ed25519-public-key` (`0444`); both are root:wheel, descriptor-rebound, and sealed before any receipt signing. A receipt records this Key-B signing key generation and public-key SHA-256. A later Key-B rotation adds a next immutable, predecessor-signed keyring record; it never rewrites Key A, bootstrap approval verification material, the V2 approval, input bundle, runtime/authority manifest, receipt, or admission record. Key A never rotates through this keyring: changing its compile-time hash requires a newly reviewed provisioner source/binary and a new Task 14 review/authorization/approval chain. A revocation adds its next immutable signed Key-B record and can make the authority inactive, but it never alters historical receipt bytes. Verification first pins bootstrap and Key A, then verifies the contiguous Key-B keyring, then receipt, then the contiguous revocation state; any gap, bad signature, unexpected version, Key-A/Key-B role confusion, or non-active final state fails closed.

The required hash graph is deliberately acyclic: the reviewed provisioner source contains the Key-A hash constant; built-helper identity and that constant independently pin held Key-A bytes; those values feed the review package; the review package feeds the separately Key-A-signed observation authorization; those two held inputs and root-only preimage observations feed the final Key-A-signed approval; bootstrap verifies Key A before storing that approval/signature/key/hash, then creates unrelated Key-B generation 1; the admission record binds only bootstrap approval, input, policy, attempt UUID, and volume; the runtime manifest binds that prior policy/approval evidence to actual stage-specific profile/command and pre/post interpreter observations plus observed output entries; the authority manifest binds checkout and runtime-manifest hash; the receipt binds the preceding immutable hashes plus Key-B identity; the detached receipt signature covers only receipt bytes. Neither source constant, review package, authorization, approval, admission record, manifest, Key-B keyring record, nor revocation record contains a future runtime/receipt/signature hash. This ordering forbids key/self-authentication, review/approval, approval/manifest, receipt/manifest, receipt/admission, or receipt/keyring cycles.

### Privilege and admission preconditions

The helper is neither setuid nor setgid, does not elevate itself, and has no daemon, XPC service, listener, socket, request protocol, or IPC endpoint. An external OS administrator must authorize its ordinary root invocation; that authorization is outside the helper and is its only elevation path. The exact root-owned cwd is `<stage>/runtime`; the helper creates `<stage>/home` and `<stage>/tmp` root:wheel `0700`. Standard input is `/dev/null`; stdout/stderr are capped root-owned pipes; no inherited file descriptors survive. The child environment is exactly the canonical ordered rows `HOME=<stage>/home`, `LANG=C`, `LC_ALL=C`, `PATH=/usr/bin:/bin`, `PIP_CONFIG_FILE=/dev/null`, `PIP_DISABLE_PIP_VERSION_CHECK=1`, `PIP_NO_INPUT=1`, `PYTHONNOUSERSITE=1`, and `TMPDIR=<stage>/tmp`; no other row exists. `-I -s -E`, `PIP_CONFIG_FILE=/dev/null`, `--isolated`, `--no-index`, `--no-deps`, `--only-binary=:all:`, and `--no-cache-dir` are all mandatory. The helper rejects, rather than clears-and-continues from, any inherited `PYTHON*`, `PIP_*`, `DYLD_*`, `VIRTUAL_ENV`, `PATH`, `HOME`, `PWD`, or unapproved descriptor. The child is in a new process group with a fixed timeout, output cap, and TERM/KILL reap protocol.

   Network is denied in depth: no downloader/resolver command exists; `--no-index --no-deps` is mandatory; the child runs under a fixed canonical Seatbelt profile whose exact bytes and SHA-256 are policy/approval-bound. The profile denies `network*`, denies reads of the bundle/homebrew/user/developer roots, denies writes outside the logical staging root, and allows only required read-only `/System` and `/usr/lib` loader paths. Inability to install/activate the exact profile is `MATERIALIZATION_SANDBOX_UNAVAILABLE`, not a warning. Process-call test adapters record and reject any network or non-fixed executable attempt.
8. **Post-install validation.** After reaping the install process, re-open/rebind/hash/Mach-O-parse/strictly-code-sign-validate the launcher and final interpreter again. The launcher must still equal its approval pin and the interpreter must exactly equal every pre-install byte/Mach-O/code-sign observation; any absence, identity loss, mutation, new invalid signature, or mismatch is terminal. From that same revalidated interpreter and fixed cwd, invoke `/usr/bin/sandbox-exec -p actual-profile final-held-interpreter-path` plus the fixed `-I -s -E -c` import-probe argv; hash this distinct actual import command and apply the same launch checks. It returns a bounded canonical report of interpreter version, imported module files, and `sys.path`. Each absolute result must be within `runtime/`; no cwd, user site, bundle, Homebrew, or external path is accepted. Re-enumerate the entire runtime, compute file and domain-separated directory digests, rerun the strict signed Mach-O/code-signature closure gate including installed extensions, and reject any byte/path/dependency drift. Rebind/hash/Mach-O/code-sign the launcher and interpreter once more after the probe before writing the runtime manifest.
9. **Seal and publish.** Copy the checkout only from the accepted root-owned `input/` copy into `authority-stage/`, construct authority and runtime manifests from held descriptors, sign the receipt with the root-only key, fsync receipt then signature, seal/rebind the complete tree, and publish once using `renameatx_np(..., RENAME_EXCL)`. Fresh verification must succeed before the authority becomes active. No runtime process is run from the final authority during this step.

The helper performs no Git operation during materialization. Git evidence is the Task 14-reviewed checkout content and bundle manifest; a live worktree cannot influence a root process after bundle admission.

## State, errors, cleanup, and retry

| State | Meaning | Result on error |
| --- | --- | --- |
| `ABSENT` | No authority, matching quarantine, or prior attempt | May admit one bundle |
| `BUNDLE_VALIDATING` | Only untrusted held reads | Stop with no user-path mutation |
| `ADMITTED` | Root-only `O_EXCL` admission record and parent fsync succeeded | Any later error is durable forensic state |
| `PRIVATE_COPY` / `EXTRACTING` / `INSTALLING` | Mutable objects are exclusively root-owned staging | Quarantine root-owned staging and retain admission |
| `POSTINSTALL_VALIDATING` | Runtime output and closure are being measured | Quarantine root-owned staging |
| `SEALED` | Receipt, signature, and all final objects revalidate | Publish exclusively or retain quarantine |
| `PUBLISHED` | Sealed authority exists | Fresh read-only verify only |
| `QUARANTINED` | Any failed/interrupted attempt | Terminal; same ID is permanently rejected |

Closed error classes include `ROOT_PRIVILEGE_REQUIRED`, `LOADED_HELPER_IDENTITY_MISMATCH`, `MATERIALIZATION_STORAGE_REJECTED`, `APPROVAL_REVIEW_PACKAGE_INVALID`, `APPROVAL_OBSERVATION_AUTHORIZATION_INVALID`, `APPROVAL_PREIMAGE_OBSERVATION_FAILED`, `APPROVAL_VERIFICATION_KEY_INVALID`, `APPROVAL_SIGNATURE_INVALID`, `KEY_ROLE_CONFUSION`, `BUNDLE_ARGUMENT_INVALID`, `BUNDLE_MANIFEST_INVALID`, `BUNDLE_APPROVAL_MISMATCH`, `BUNDLE_DESCRIPTOR_REBIND_FAILED`, `LOCK_ARTIFACT_MISMATCH`, `ADMISSION_CREATE_FAILED`, `ADMISSION_FSYNC_FAILED`, `PRIVATE_STAGE_INVALID`, `ARCHIVE_UNSAFE`, `EXTRACTED_RUNTIME_RENAME_FAILED`, `BASE_RUNTIME_LOADER_REJECTED`, `SANDBOX_LAUNCHER_MISMATCH`, `INTERPRETER_IDENTITY_MISMATCH`, `MATERIALIZATION_SANDBOX_UNAVAILABLE`, `PIP_EXIT_NONZERO`, `PROCESS_TIMEOUT`, `PROCESS_OUTPUT_LIMIT`, `IMPORT_CONFINEMENT_FAILED`, `POSTINSTALL_CLOSURE_REJECTED`, `CODESIGN_IDENTITY_MISMATCH`, `SEAL_READBACK_FAILED`, `PUBLISH_EXCLUSIVE_UNAVAILABLE`, and `PRIOR_ATTEMPT_EXISTS`. Errors disclose fixed error codes and bounded logical names only; they never log private keys, bundle contents, environment, or arbitrary paths.

On success, the helper may remove only its own verified `materialization-work/<attempt>` children after the authority has been published and every child is still root-owned, beneath the fixed work parent, no-follow rebound, unsealed, and unlinked from published authority objects. It preserves the immutable/durable admission record and binds its hash in the receipt. It never deletes, renames, chmods, chflags, or recursively cleans the user bundle, downloads, checkout, prior authority, prior quarantine, old custody root, or any user-owned residue. On failure after admission it atomically moves the verified root-owned attempt to the fixed quarantine parent and preserves the admission record; if that move cannot be proven, it leaves the root-owned work attempt in place and classifies it as quarantine. Neither case is auto-cleaned, adopted, resumed, unsealed, overwritten, or retried with the same authority ID.

Signals use the same rule: before publication, attempt best-effort descriptor-authenticated quarantine and exit nonzero; after a partial seal/publish, retain immutable forensic state and exit nonzero. A subsequent invocation seeing an authority, work residue, or matching quarantine fails closed. No user-owned pathname is used as a cleanup target.

## Rollout and risk

1. Implement and review the V2 schemas, Python no-execution boundary, Swift materializer, and disposable-root tests without privileged actions.
2. Build the reviewed Developer-ID candidate helper containing the Key-A public-key SHA-256 constant and Task 2c review package, run the exact Task 14 evidence gates, then obtain a Key-A-signed observation authorization and run the root-only no-child preimage ceremony to produce/sign the final approval naming the exact commit and V2 approval SHA-256.
3. Only then may the separately authorized bootstrap/materialize-and-provision/verify ceremony occur. A materialization failure is terminal for this authority ID.
4. Only a fresh successful protected receipt plus a separate explicit Task 15 approval may affect custody. This design does not grant that approval.

The remaining material risk is the trusted administrator/root/bootstrap and the audited installer itself: root can always defeat this boundary. The design reduces the same-UID adversary's influence to a fully revalidated input transport and fails closed if Darwin's filesystem, sandbox, immutable-flag, code-signing, or no-replace guarantees cannot be demonstrated. It does not claim to make a user-owned bundle authoritative.

## Self-review

This specification has no unresolved implementation choice, alternate execution route, implicit cleanup, caller-configurable authority path, or unbound artifact input. The sole child launcher is `/usr/bin/sandbox-exec`; its descriptor identity, byte hash, strict Apple code-sign identity, exact `-p` profile literal, and final held interpreter argv are approval- and receipt-bound. Key A is an external pre-bootstrap approval-verification public key whose hash is compiled into reviewed provisioner source; bootstrap verifies held Key-A bytes before approval signature verification and then seals only the public key. Key B is independently generated generation-1 receipt/authority signing material under `control/keyring`, never authenticates an approval, and alone rotates/revokes. Task 2c emits only a review package; a separately Key-A-signed root no-child preimage ceremony produces the final approval before bootstrap, so no approval field depends on runtime/receipt output and the graph remains acyclic. The interpreter has independent required strict code-sign and byte/Mach-O observations before installation, after installation, and after the probe; no unsigned/invalid exception remains. The old Task 8 plan clauses are explicitly non-authoritative pending its approved amendment. The illustrative schema value markers are explicitly non-production examples; Task 14 requires concrete values. The bootstrap pin, V2-only parsers, admission record, extracted-to-final rename, sandbox/child command domain, manifests, receipt, rotation/revocation chain, and cleanup rules are acyclic and use the same V2 evidence graph: approval-bound bundle inputs become root-observed sealed runtime outputs. Production and old evidence custody remain outside scope.
