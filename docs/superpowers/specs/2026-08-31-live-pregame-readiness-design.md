# Pregame diagnostics and readiness

## Approved scope

The user approved the proposed approximately two-hour scope: distinguish missing pregame evidence from actual starter disagreement; test missing-to-complete-to-changed participant observations; provide a per-game readiness table. This records that accepted design, not a new model or infrastructure project.

## Reason semantics

`STARTER_CONFLICT` means that for at least one side both schedule-probable and observed starter IDs are present and valid, and those IDs differ. Missing schedule-probable, missing/ambiguous observed pitcher evidence, and incomplete lineup evidence retain accurate missing/invalid reason codes. Multiple independent causes may coexist. Missing IDs are never substituted with guesses or silently treated as confirmed. Invalid/ambiguous participants remain unscored. Existing scoring eligibility is not relaxed.

Keep current snapshot freshness, final schedule revalidation, raw response and receipt binding. The main V1 JSON key set, ranking cap and scoring/model formulas remain unchanged. New observations may have corrected reason lists and corresponding hashes; archived reports and their bytes stay untouched.

## Input-change tests

Exercise the real parser and service/CLI pipeline with fixture HTTP responses at the external boundary. Verify incomplete participants produce no score and truthful missing reasons; complete matching participants and valid nine-player lineups reach the existing scorer; changed observed/schedule starter evidence rejects that game. Verify actual mismatch, missing schedule-probable, empty pitcher lists and incomplete lineups independently. Existing exact probabilities for unchanged complete fixtures must remain identical. Label all fixture outputs synthetic; never present them as real picks.

## Readiness table

Create an additional human-readable `.readiness.md` artifact beside the existing report, without expanding the primary JSON contract. Show every scheduled game represented in the same live observation: game/team identity, expected and observed starters (IDs at minimum, names only if available), side-specific lineup counts, observation/check timestamps with timezone, and missing/conflicting evidence. Use existing captured objects and bound receipts; no extra HTTP calls just to render this view. Preserve provenance by linking the main report and referring to its canonical content digest, schedule/participant observation identities and receipt/raw digests.

State clearly that participant completeness is not a betting recommendation or proof that all scoring gates pass. Distinguish initial participant observation time from later final-schedule checks; do not label an old boxscore with a newer schedule time. Missing values display as unknown, never zero pitcher IDs or fabricated names. Escape external names for Markdown. Use existing no-overwrite/safe report persistence patterns and fail visibly if a promised diagnostic artifact cannot be persisted; preserve any already-written report evidence.

Concrete view mapping: schedule `away/home_probable_pitcher_id` and `away/home_probable_pitcher_name` are expected starters; participant `away/home_pitcher_list_id` is observed pitcher-list evidence (no invented observed name). `len(away/home_lineup)` counts validated lineup entries, not raw roster size; label it accordingly. A missing participant observation is unknown rather than zero. Use that game's `LIVE_PARTICIPANTS` binding `durable_at_utc` as the explicitly labeled recorded-observation time and show its binding digest; keep later final-check timestamps separate. Pair the table with the primary run's recorded classification/reasons where present without pretending non-Top-3 games have exported scores.

Persist to the primary report basename plus `.readiness.md` through the same held `TrustedRoot`, exclusive write and secure readback patterns. Keep `run_daily_top3`'s existing return tuple unchanged; derive the companion path deterministically for CLI display.
